Основной UI сделан через UI Toolkit. Не возвращайся к созданию всего интерфейса программно через старый Canvas. При изменении адаптивности проверяй несколько aspect ratio и `PanelSettings`: проблема слишком маленького интерфейса ранее исправлялась масштабированием UI на весь экран.

### Spring

Пакеты:

- `auth` — регистрация, вход, BCrypt, JWT, роли.
- `player` — профиль, интересы и административное управление аккаунтами.
- `daily` — ежедневные задания, серия, награды и коины.
- `learning` — каталог проверенных вопросов, попытки, ответы, оценка и персональные уроки.
- `market` — акции, цены, новости, портфель, заявки, рейтинг и игровые дни.
- `quiz` — старый каталог вопросов, используемый админкой; не путать с основным `learning`.
- `ml` — клиент классификации интересов через FinStory.

Сервер является источником истины для очков, денег, коинов, наград, ответов, уроков и ролей. Клиент не должен самостоятельно начислять эти значения.

### FinStory

Каталог: `FinStory_service`. Сервис получает тему, ошибки и интересы и возвращает структурированный учебный материал: историю, героя, объяснение, вывод и термины. История персонализируется по ответам и интересам, но модель не дообучается отдельно на каждом пользователе.

Не вставляй Yandex/Gemini API-ключи в исходники, документацию, логи или коммиты. Используй существующие переменные `.env`; значения ключей не выводи.

## Обучение

- `LearningCatalog` содержит 4 темы и 16 проверенных вопросов.
- Диагностика берёт вопрос из каждой темы.
- Обычный квиз использует 5 вопросов, тематический — 3.
- Правильный индекс не отправляется при старте попытки.
- Ответ фиксируется сервером; принятый ответ нельзя заменить.
- Завершение попытки идемпотентно.
- По 10 очков начисляется только за впервые правильно решённый уникальный вопрос.
- После попытки создаётся один урок по слабой теме.
- История персонализируется по ошибкам и интересам.
- В UI показывается состояние генерации, чтобы пользователь понимал, что история ещё загружается.
- Термины входят в `LessonContent` и сохраняются в PostgreSQL внутри JSON урока.

## Ежедневная серия, задания и экономика

Реализовано:

- ежедневная серия хранится на сервере;
- последовательный календарный день увеличивает серию;
- пропуск сбрасывает её до одного;
- хранится лучшая серия;
- задания: пройти один тест и сыграть один раз в мини-игру;
- первое подходящее действие ставит прогресс `1/1`;
- награда за 7 дней: `4` коина и `2000` денег биржи;
- награда за 14 дней: `8` коинов и `3000` денег биржи;
- повторное получение награды блокируется сервером;
- обмен в магазине: `1` коин = `1000` виртуальных денег биржи;
- справа сверху есть счётчики серии и коинов;
- нажатие открывает окна наград и магазина.

Следующие награды после 14 дней пока не определены. Не придумывай баланс без согласования с пользователем.

## Мини-игры

Есть раздел мини-игр и прототип кликера «Офис мечты». Сейчас экран кликера в основном представляет большую кнопку; первый клик может засчитать ежедневное задание. Полная экономика офиса ещё не реализована.

Планируемая механика: пользователь кликает для дохода, покупает отделы, повышает их уровни, нанимает сотрудников и получает пассивный доход. Для масштабирования нужны серверные сущности прогресса офиса и конфиг каталога отделов; нельзя хранить значимый прогресс только в `PlayerPrefs`.

## Админ-панель

Адрес локально:

```text
http://localhost:8080/admin.html
```

Панель защищена ролью `ADMIN`. Обычный игрок получает `403`. Реализовано:

- список и поиск аккаунтов;
- просмотр id, email, nickname, роли и даты регистрации;
- просмотр интересов, денег, коинов, уровня и очков;
- просмотр текущей/лучшей серии и ежедневных счётчиков;
- просмотр полученных наград;
- число попыток, уроков и позиций портфеля;
- изменение редактируемых данных аккаунта;
- назначение `PLAYER`/`ADMIN`;
- добавление 1–365 дней к серии для тестирования;
- сброс отметок о полученных наградах;
- изменение интервала рынка и пропуск игровых дней;
- управление старым каталогом вопросов.

Пароль не отображается и не редактируется: в БД хранится только BCrypt-хеш. На момент последней проверки в локальной БД не было постоянного ADMIN-аккаунта. Чтобы назначить первого администратора, пользователь должен зарегистрироваться, указать email в `IVR_ADMIN_EMAILS` в `.env` и перезапустить Spring.

Связанные endpoints:

```text
GET    /admin/players
PUT    /admin/players/{id}
POST   /admin/players/{id}/streak/advance
DELETE /admin/players/{id}/streak/rewards
GET    /admin/market/state
PUT    /admin/market/interval
POST   /admin/market/skip
```

## База данных

PostgreSQL использует Flyway, Hibernate работает в режиме `validate`. Текущие миграции включают роли, ежедневную активность, коины и отметки наград. Основные таблицы:

- `players`, `player_progress`;
- `daily_progress`, `streak_reward_claims`;
- `learning_attempts`, `personal_lessons`;
- `stocks`, `price_points`, `news_events`, `market_state`;
- `holdings`, `market_orders`;
- старый каталог `questions`.

Любое изменение persisted-схемы PostgreSQL оформляй новой Flyway-миграцией. Не редактируй уже применённую миграцию ради нового поля.

## CI/CD и хостинг

- GitHub Actions запускает тесты Spring на push и pull request.
- Pipeline собирает backend Docker image и публикует его в GHCR для `main`/`v*`.
- Есть ручной workflow WebGL; ему нужны Unity license secrets.
- Это continuous delivery. Полное автоматическое развёртывание на домен ещё не настроено, потому что VPS/хостинг и deploy-token не выбраны.
- Для публичного стенда нужен VPS с Docker Compose, HTTPS reverse proxy, доменом, PostgreSQL volume и секретами среды.

Не называй автодеплой готовым, пока push действительно не обновляет выбранный сервер и не проходит smoke-check публичного URL.

6. Компетенции: Unity, ML/Data Science, UX/UI, аналитика, геймификация и поведенческая экономика.

### Исходный поэтапный план

1. Исследование ЦА и рынка (~3 недели): гипотезы, анкеты и интервью, вторичные данные, обработка результатов.
2. Анализ банковских и небанковских аналогов (~1,5 недели): сбор решений, сильные/слабые стороны, выводы.
3. Концепция игры (~2 недели): общая концепция, CJM, согласование.
4. Механики, сценарии и контент (~2 недели): единый документ, диаграмма Ганта, MoSCoW.
5. MVP (~4 недели): архитектура и репозиторий, Unity-механики, UI/UX, backend/БД, внутреннее тестирование.
6. Тестирование ЦА и A/B-тесты (~2 недели): группа, сценарий и метрики, тест, анализ.
7. Доработка (~3 недели): правки, механики, контент и материалы защиты.

### Риски из исходной заявки

1. Неверное понимание аудитории — сочетать интервью, опрос и раннюю проверку гипотез.
2. Переусложнение механик — сначала реализовать упрощённое ядро.
3. Технический долг — code review, документация и внутреннее тестирование.
4. Несовместимость backend и ML — заранее согласовать API и форматы.
5. Неравномерная нагрузка — распределить задачи и синхронизироваться.
6. Недостаток реальных данных — использовать открытые и собирать собственные игровые события с согласия пользователей.

## Техническое задание проекта

Полная редактируемая версия находится в `docs/TECHNICAL_SPECIFICATION.md`. Ниже — обязательный контекст ТЗ для другого AI.

### Назначение и формат

Браузерная обучающая игра Unity WebGL для аудитории 14–22 лет. Backend — Kotlin/Spring Boot, данные — PostgreSQL. Цель: коротко обучать финансовой грамотности, диагностировать слабые темы, разбирать ошибки и давать безопасную практику через учебный рынок и игровые механики.

### Граница MVP

В MVP входят регистрация, вход, онбординг, диагностика, тематические квизы, персональные уроки и истории, повторение, серия, два ежедневных задания, коины, магазин обмена, профиль, учебная биржа, рейтинг, раздел мини-игр и админка. Полная экономика кликера, реальные бонусы, восстановление пароля, подтверждение email, расширенная социальная система и production-хостинг остаются развитием.

### Функциональные требования

1. Регистрация по email, паролю и никнейму; пароль — BCrypt, ответ — JWT.
2. Вход и восстановление действующей сессии.
3. Онбординг и сохранение интересов.
4. Диагностическая попытка без раскрытия правильных индексов.
5. Серверная фиксация и проверка каждого ответа.
6. Идемпотентный результат и серверное начисление очков.
7. Персональный урок по слабой теме после ошибок.
8. Повторный тест по уроку и завершение при результате от 50%.
9. Рабочий fallback при недоступности внешней модели.
10. Профиль с учебными и игровыми показателями.
11. Акции, цены, история и новости учебного рынка.
12. Атомарные операции BUY, SELL, SHORT, COVER.
13. Рейтинг по наличным и рыночной стоимости портфеля.
14. Административные операции только для роли ADMIN.
15. Безопасный выход с удалением локальной сессии.
16. Серверная ежедневная серия.
17. Два ежедневных задания: тест и мини-игра.
18. Серверные награды серии и защита от повторной выдачи.
19. Коины и обмен `1 : 1000` на деньги учебной биржи.
20. Админ-панель для аккаунтов, серии, рынка и вопросов.

### Нефункциональные требования

1. Пароли не возвращаются API и не хранятся открыто.
2. Игровые API защищены JWT.
3. Пользователь не может читать чужие попытки и уроки.
4. Схема PostgreSQL изменяется через Flyway.
5. Серверные тесты запускаются `./gradlew test`.
6. UI показывает загрузку и ошибки, не допускает двойные запросы.
7. Подтверждённые ответы не теряются.
8. WebGL работает в современных браузерах и адаптируется к экрану.
9. Секреты не попадают в Git.
10. Документация позволяет запустить проект новому разработчику.
11. Сервер остаётся источником истины для ответов, денег, наград и ролей.
12. Внешняя AI-генерация не блокирует основной маршрут.

### Критерий готовности для защиты

- согласованный список пользовательских сценариев реализован и показан;
- тесты проходят;
- полный acceptance-маршрут проходит без блокирующих ошибок;
- WebGL и API доступны проверяющему по публичной ссылке;
- GitHub содержит код, сценарии, UML, архитектуру и инструкции;
- подготовлено демонстрационное видео 5–10 минут;
- нет ошибок, приводящих к потере прогресса, двойной награде или чужому доступу;
- подготовлены отчёт, рефлексия, презентация и доказательства исследования ЦА.
