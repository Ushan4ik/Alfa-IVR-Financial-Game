# Состояние проекта и план развития

Аудит основан на текущем коде Unity и Spring. «Реализовано» означает, что функция имеет код и связанный пользовательский либо серверный сценарий. Это не всегда означает готовность к публичному production-запуску.

## Что уже реализовано

### Пользователь и вход

- Стартовый экран с переходами к регистрации и входу.
- Регистрация с nickname, email, паролем и повтором пароля.
- Клиентская проверка полей регистрации.
- Вход по email и паролю.
- Хэширование паролей через BCrypt на сервере.
- JWT-сессия сроком на 7 дней.
- Сохранение JWT в Unity `PlayerPrefs`.
- Автоматическое восстановление сессии при запуске.
- Выход из аккаунта и очистка локальной сессии.
- Профиль с nickname, email, уровнем, очками и интересами.

### Онбординг

- Последовательность из пяти onboarding-слайдов.
- Возможность пропустить информационные слайды и перейти к интересам.
- Сохранение интересов пользователя.
- Вызов внешнего ML-сервиса для классификации интересов.
- Безопасный fallback `другое`, если ML-сервис недоступен.
- Повторное редактирование интересов из профиля.
- Автоматический запуск вводного теста после первой регистрации.

### Главное меню

- Единая оболочка Hub на UI Toolkit.
- Вкладки Home, Learn, MiniGames, Quests, Rating, Profile и Market.
- Общая нижняя навигация.
- Отображение текущего уровня и очков.
- Карточки базовых тем.
- Результат квиза после возвращения из отдельной сцены.
- Автоматическое открытие созданного разбора ошибок.
- Обработка истёкшей сессии при получении 401.
- Отображение текущей ежедневной серии рядом с очками.

### Квиз

- Отдельная сцена квиза.
- Загрузка вопросов с Spring API.
- Диагностический, общий, тематический и повторный режимы.
- Отображение прогресса по вопросам.
- Блокировка изменения уже принятого ответа.
- Серверная проверка каждого ответа.
- Подсветка правильного и неправильного вариантов.
- Объяснение ответа.
- Экран результата.
- Пауза и выход в главное меню.
- Повтор сохранения результата после сетевой ошибки.
- Идемпотентное завершение попытки на сервере.
- Локальная тренировка, если сервер недоступен.

### Персональное обучение

- 4 проверенные финансовые темы.
- 16 серверных вопросов.
- Хранение снимка вопросов и ответов каждой попытки.
- Расчёт слабой темы пользователя.
- Прогресс по темам на основе истории ответов.
- Создание одного персонального урока после попытки.
- Разбор неправильных ответов.
- Короткий пример и шпаргалка.
- Повторный тест по слабой теме.
- Подбор в повторном тесте вопросов, которых не было в исходной попытке.
- Завершение персонального урока после успешного повторения.
- Серверный fallback-урок, который работает без внешней модели.
- Необязательная генерация объяснения через Gemini.
- Очередь уроков `PENDING → READY/FALLBACK`, сохраняемая в БД.
- Начисление очков только за впервые правильно решённые уникальные вопросы.
- Серверный расчёт уровня и награды.

Текущая персонализация анализирует ответы и темы. Собственная ML-модель на данных пользователя не обучается.

### Базовые уроки

- Карточки «Накопления», «Вклады», «Страхование», «Кредиты».
- Текст, описание и квиз для каждой карточки.
- Локальная отметка прохождения.
- Отображение количества завершённых карточек.

### Задания

- Два ежедневных задания, которые сервер хранит отдельно для каждого игрока:
  - пройти один тест;
  - сыграть один раз в мини-игру.
- Задание за тест обновляется автоматически только при первом завершении попытки.
- Повторный запрос завершения того же теста не увеличивает прогресс.
- Задание мини-игры доступно: первый клик в «Офисе мечты» отправляет результат на сервер и устанавливает прогресс `1/1`.
- Ежедневный прогресс сбрасывается при первом входе в новый календарный день.
- Фильтры, индикаторы прогресса и кнопка перехода к тесту.

### Ежедневная серия

- Серия хранится на сервере в PostgreSQL и не зависит от устройства или `PlayerPrefs`.
- Первый вход в следующий календарный день увеличивает серию на один.
- Пропуск календарного дня начинает новую серию с одного дня.
- Хранится лучшая серия пользователя.
- Календарный день рассчитывается в зоне `Europe/Moscow`, которую можно изменить через конфигурацию.
- За 7 дней можно один раз получить 4 коина и 2000 виртуальных денег биржи.
- За 14 дней можно один раз получить 8 коинов и 3000 виртуальных денег биржи.
- Получение награды защищено сервером от повторного начисления.

### Коины

- Баланс коинов хранится на сервере отдельно для каждого игрока.
- Счётчик коинов и серия доступны в правой части верхней панели.
- По нажатию на серию открывается список наград и срок до следующей награды.
- По нажатию на коины открывается первый экран магазина.
- Доступен атомарный обмен одного коина на 1000 виртуальных денег биржи.

### Учебный рынок

- Симуляция игровых дней.
- Акции, секторы и изменение цены.
- История цены.
- Игровые новости и настроение новости.
- Портфель пользователя.
- Денежный баланс и общая стоимость капитала.
- Покупка, продажа, короткая позиция и её закрытие.
- Серверная проверка операций.
- Автоматический шаг рынка по расписанию.
- Административная смена интервала и пропуск игровых дней.
- Автоматическое создание начального состояния рынка.

### Рейтинг

- Серверный рейтинг игроков по стоимости виртуального капитала.
- Подиум первых трёх мест.
- Общий список.
- Выделение текущего пользователя.
- Ручное обновление рейтинга.

### Backend и данные

- Spring Boot REST API.
- PostgreSQL для локальной разработки через Docker Compose.
- H2 для автоматических тестов.
- JPA-сущности и репозитории пользователей, обучения и рынка.
- CORS для браузерного клиента.
- Интеграционные тесты персонального обучения.
- Статическая административная страница.
- Разделение серверного кода на auth, player, daily, learning, market, quiz и ml.
- Flyway-миграции V3–V4 с ежедневной активностью, коинами и полученными наградами серии.
- Интеграционные тесты последовательной серии, сброса после пропуска дня и однократного зачёта теста.

### Подготовка к WebGL

- Unity использует HTTP API, совместимый с WebGL.
- CORS разрешает запросы браузера.
- Основные экраны реализованы на UI Toolkit.
- Адрес Spring API задаётся в `AppEntry`.
- Локальная WebGL-сборка запускается через `build-web.sh` и раздаётся Nginx на порту 8081.
- WebGL-сборка на Unity 6000.4.6f1 проверена в браузере: регистрация, квиз, персональный урок и рынок работают с Spring/PostgreSQL.

### CI/CD

- GitHub Actions запускает интеграционные тесты Spring для push и pull request.
- Pipeline собирает production Docker-образ и публикует его в GitHub Container Registry после push в `main` или тега `v*`.
- Отдельный ручной workflow собирает WebGL-артефакт после настройки Unity license secrets.
- Production-профиль требует пароль БД, JWT secret и разрешённые CORS origins через переменные среды.

## Что уже можно масштабировать

### Контент обучения

`LearningCatalog` позволяет добавлять новые темы и вопросы. Для текущего объёма достаточно добавить тему, проверенный материал и набор вопросов. Следующий этап — перенести управление контентом в БД и административный интерфейс, чтобы выпускать уроки без пересборки Spring.

### Персональные уроки

Попытки и уроки уже принадлежат конкретному пользователю и хранятся в PostgreSQL. Можно увеличивать число тем, строить историю знаний, интервальное повторение и рекомендации. Серверный fallback позволяет масштабировать обучение независимо от доступности Gemini.

### UI

`ScreenManager` позволяет добавлять верхнеуровневые экраны, а Hub — вкладки. UXML и USS отделены от C#-логики. Для роста приложения нужно продолжить разделение `HubScreen` на отдельные контроллеры разделов.

### API

Unity обращается к серверу через сервисы `AuthService`, `DailyService`, `LearningService`, `MarketService`. Новую серверную функцию можно добавить отдельным DTO и методом сервиса, не помещая HTTP-код в экран.

### Игровой рынок

Модель уже поддерживает несколько акций, секторов, новости и разные виды заявок. Можно добавлять новые активы и игровые события. При большом числе игроков потребуется оптимизация запросов и отделение расчёта рынка от основного API.

### Мини-игры

- В нижнюю навигацию добавлена отдельная вкладка «Игры».
- Каталог строится из `MiniGameCatalog`, поэтому новую карточку можно добавить без изменения разметки Hub.
- В каталоге показаны «Офис мечты», «Финансовая корзина» и «Пары терминов» с длительностью и статусом готовности.
- «Офис мечты» запускается внутри Hub и пока состоит из одной большой кнопки со счётчиком кликов.
- Кнопки ещё неготовых игр заблокированы, чтобы пользователь не попадал в пустую сцену.
- `GameManager`, `QuizConfig` и `MiniGameResult` задают основу перехода в отдельную игровую сцену и возврата результата.
- Первый клик вызывает `POST /daily/minigame-completed`; повторный вызов не увеличивает ежедневный прогресс выше `1/1`.

Чтобы подключить игру, нужно создать её сцену, добавить сцену в Build Settings и записать имя сцены в соответствующий элемент `MiniGameCatalog`. После завершения игра должна вернуть результат через `GameManager` и вызвать `DailyService.CompleteMiniGame()`.

## Чего не хватает до публичного запуска

### Критично

1. **Роли и защита административного API выполнены.** Введены PLAYER/ADMIN; `/admin/**` и изменение каталога вопросов требуют ADMIN. Перед публикацией остаётся настроить реальный административный аккаунт и проверить процесс ротации доступа.
2. **Изоляция debug-компонентов выполнена.** `ApiTest` и `TestUI` удалены из `Main.unity`; перед публичной сборкой нужен отдельный контроль development-сцен и define symbols.
3. **Миграции БД подключены.** Flyway управляет PostgreSQL, Hibernate валидирует схему. До production остаются резервное копирование и регламент отката.
4. **Production-конфигурация контейнера выполнена.** Пароль БД, JWT secret, CORS origins и внешние ключи поступают через переменные среды. Для публичного стенда остаётся выбрать secret storage хостинга.
5. **WebGL build и end-to-end проверка выполнены.** Unity 6000.4.6f1 собирает клиент; регистрация, квиз, персональный урок и рынок проверены в браузере.
6. **Ограниченный CORS выполнен для production-профиля.** Посторонний origin отклоняется. HTTPS появится вместе с выбранным публичным доменом и reverse proxy хостинга.
7. **Серверная валидация входных данных.** Нужны ограничения email, пароля, nickname, количества сделки, размеров текстов и единый формат ошибок.

### Нужно для стабильности

- Refresh token либо контролируемое повторное получение сессии.
- Rate limiting на вход, регистрацию, ответы и генерацию уроков.
- Блокировка brute force и журнал событий безопасности.
- Централизованная обработка 401, timeout и недоступности сети в Unity.
- Мониторинг API, БД, очереди Gemini и scheduler рынка.
- Структурированные логи и идентификатор запроса.
- Health/readiness endpoints для API и БД.
- Резервные копии PostgreSQL и проверка восстановления.
- Pagination для рейтинга, вопросов, уроков и истории операций.
- Ограничение роста истории цен, попыток и ответов.
- Защита фоновой очереди Gemini при запуске нескольких экземпляров сервера.
- Повтор запросов Gemini с backoff и лимитом попыток.
- Отмена async-операций Unity при закрытии экрана.
- Экран состояния «нет сети» и понятное восстановление.

### Не хватает продуктовых функций из макетов

- Полный магазин товаров и бонусов; сейчас доступен только обмен коина на деньги биржи.
- Дополнительные способы заработка коинов помимо наград за серию.
- Настройки звука, языка, уведомлений и аккаунта.
- Полноценная статистика пользователя.
- Особые и недельные квесты, награды и редактируемый каталог заданий.
- Экран календаря серии; награды за 7 и 14 дней уже реализованы.
- Полная экономика кликера: отделы, уровни отделов, сотрудники, стоимость улучшений, пассивный доход и серверное сохранение прогресса.
- Награды за квесты.
- Push/email-напоминания.
- Восстановление пароля и подтверждение email.
- Удаление аккаунта и экспорт пользовательских данных.
- Административное управление учебными материалами.

## Что можно оптимизировать в текущем коде

### Unity

- Разделить `HubScreen` на `HomePanel`, `LearningPanel`, `QuestPanel`, `RatingPanel`, `ProfilePanel`. Сейчас один файл управляет слишком многими сценариями.
- Удалить или изолировать `LoginManager`, `StockMarketUI`, `LeaderboardUI`, `QuestionService`, `ApiTest`, `TestUI`.
- Убрать `PlayerService.UpdateProgress` и `UpdateProgressRequest`, потому что сервер запрещает клиентское начисление очков.
- Перенести completion базовых уроков из `PlayerPrefs` на сервер.
- Добавить конфигурацию URL API для dev/staging/production вместо ручного изменения Inspector.
- Заменить строковые имена элементов UXML константами или небольшими view-binding классами.
- Проверять отсутствие UXML-элемента до подписки на событие, чтобы ошибка дизайна давала понятный лог.
- Ввести единый компонент loading/error/retry.
- Добавить Unity EditMode-тесты сервисной логики и PlayMode-тесты навигации.
- Проверить адаптивность на разных соотношениях сторон, мобильный ввод, safe area и экранную клавиатуру.

### Spring

- Разделить административные и пользовательские разрешения.
- Продолжать изменять PostgreSQL только новыми Flyway-миграциями.
- Перенести `LearningCatalog` в управляемый каталог БД с версиями вопросов.
- Не хранить весь снимок попытки только в JSON, если нужны сложная аналитика и большие объёмы; выделить ответы в таблицу.
- Добавить индексы по `playerId`, status, createdAt, stockId и полям рейтинга после анализа реальных запросов.
- Считать рейтинг оптимизированным SQL-запросом или материализованным представлением вместо загрузки большого набора объектов.
- Добавить pagination и DTO-валидацию.
- Удалить устаревший `/player/progress` после обновления всех клиентов.
- Явно версионировать API, например `/api/v1`.
- Использовать распределённую очередь или блокировку для Gemini worker при горизонтальном масштабировании.

### Персонализация

- Не отправлять каждый правильный/неправильный ответ в Gemini отдельно.
- Сначала рассчитывать слабые темы и историю на сервере, а модели передавать компактный проверенный контекст.
- Добавить интервальное повторение: повтор через 1, 3, 7 и 14 дней в зависимости от ошибок.
- Хранить сложность вопроса и оценивать уровень знания темы, а не только количество правильных ответов.
- Создавать рекомендации детерминированно, а Gemini использовать для формы объяснения.
- Добавить ручную проверку и версии промпта для качества и воспроизводимости.
- Не использовать ответы несовершеннолетних для внешнего обучения модели без отдельной юридической и пользовательской процедуры согласия.

## Приоритетный roadmap

### Этап 1 — стабильный прототип

1. Поддерживать debug-компоненты только в отдельных development-сценах.
2. **Выполнено:** собрать и проверить WebGL.
3. Настроить административный аккаунт через серверную конфигурацию и проверить аудит доступа.
4. Добавлять дальнейшие изменения схемы только отдельными Flyway-миграциями.
5. **Частично выполнено:** production CORS и контейнер готовы; URL и HTTPS зависят от выбранного хостинга.
6. **Выполнено:** провести полный сценарий регистрация → onboarding → тест → разбор → повтор → рынок.

### Этап 2 — закрытая проверка с пользователями

1. Перенести прогресс базовых уроков и квесты на сервер.
2. Добавить восстановление пароля и подтверждение email.
3. Ввести мониторинг, резервные копии и rate limiting.
4. Добавить PlayMode/E2E-тесты.
5. Собрать аналитику прохождения без хранения лишних персональных данных.
6. Проверить мобильную адаптивность и доступность.

### Этап 3 — масштабирование продукта

1. CMS/админка учебного контента.
2. Версии вопросов и эксперименты с программой обучения.
3. Очередь генерации и несколько экземпляров Spring.
4. Pagination, индексы, кэш рейтинга.
5. Серверные квесты, награды, монеты и магазин.
6. Дополнительные мини-игры.
7. Интервальное повторение и более точная модель знаний пользователя.

## Общая оценка

Проект уже является связным full-stack прототипом: есть аккаунт, меню, серверный квиз, персональный разбор, прогресс и учебный рынок. Архитектура позволяет добавлять контент, экраны и API-сервисы. Главные препятствия для масштабирования сейчас связаны не с дизайном меню, а с production-безопасностью, миграциями БД, WebGL-проверкой, разделением крупных UI-контроллеров и переносом локального прогресса на сервер.
